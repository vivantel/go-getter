## Decision

Supersedes 0068 (v0.2 and v0.3 shipped as it set out; only the order after v0.3 changes).

- **v0.4**, in this order:
  1. **Autonomous run contract and approve-once for outward commands** (backlog L.8, issue #91): a run states up front what it may do unattended, and an outward-facing command such as `gh pr merge` is approved once per user, reusing the secret-approval machinery of 0126.
  2. **Testing, coverage, debugging; memory beyond the knowledge base.**
- **Later, provisional and in this order**: host adapters (L.10, #84-#89); cross-plan "what's next" (L.6, #90); third-party packs and helpers (L.9, #92); MCP governance (L.11, #93); go-getter as an MCP server (L.12, #94); then the execution sandbox, release, review, docs and the remaining SDLC packs, and the later slices of the sanitization layer.
- The order after v0.4 is provisional; it is re-evaluated when v0.4.0 ships.

## Why

The owner chose (2026-10-11) to put the autonomy contract first: the secret-use work (0126) showed that default-path friction for agents is a product defect, and unattended runs hit the same friction on every outward command. Testing and memory stay in v0.4 as 0068 planned. Adapters, helpers and MCP build on a settled run contract and approval model, so they come after.

## Tradeoffs considered

- **Testing and memory first (0068's order)**: no new product surface needed, but unattended runs keep stopping at outward commands.
- **Host adapters first**: widens host support sooner, but each adapter would implement approvals that L.8 is about to change.
- **Cost accepted**: v0.4 starts with a design-heavy item (an interview) before any deterministic work.
