## Decision

1. **Claim.** All live claims are entries in one ledger, the remote ref `refs/go-getter/claims`, a commit whose tree holds `ledger.json`. An entry records the unit, the holder (kind `human|agent|ci`, and an id), the scope tokens, the `created` time, the lease expiry, the brief version (0173), the state (`claimed` or `parked`), the grant (0171), the parent claim it was delegated from and, for a unit created by delegation that has not merged yet, its brief fields (scope, `Accept`, what to do, `Done-when`, budget), capped in size (a pack answer, default 8 KB; a larger brief spills to the tracker issue). The brief version is a hash of those fields only (0173 item 6). When the work merges, its PR writes the unit into the plan file and the ledger copy is dropped, so a delegated child is visible and claimable at once, without a gate-and-queue cycle first. To claim, a worker fetches the ledger, checks in that version that the unit, its ancestors, its descendants and its scope do not overlap a live entry (0167), appends its entry, and pushes the new ledger as a compare-and-swap against the version it read (`--force-with-lease`); a rejected push re-fetches, re-checks and retries. The ledger's own atomic update is the only ordering, so exactly one of two overlapping claimants succeeds and no clock is read. A claim covers its unit's subtree: a descendant is claimed only as a delegation by the ancestor's holder, and an ancestor cannot be claimed while someone else holds a descendant. Renewal, parking and release are compare-and-swap updates of the same entry. The ledger's commit history is never rewritten, so it is also the record of every holder of every unit (0172 item 2).
2. **Lease and renewal.** The lease depends on the holder's kind (pack answers; defaults: agent 60 minutes, ci the job's time limit, human 8 hours). It is renewed by `heartbeat`, by every `go-getter` verb and by the generated pre-commit and pre-push git hooks, so a worker that cannot run a timer (a host agent in a long tool call) is still renewed by its own commits and verbs. Renewal changes only the ledger, never a file in the working tree and never the tracker, and is pushed only when less than half the lease remains, so frequent verbs and commits do not each cost a push; offline, renewal is skipped and the lease runs on. **A unit with live child units has no lease:** its claim ends when all its children are done, cancelled or superseded, or when its holder releases it; accountability for it is the `Owner-id`, not the holder's heartbeat. If its holder neither acts on the unit nor renews any child for `parent-idle` (a pack answer, default 7 days), the unit is parked with an ask to its `Owner-id`, so a holder who vanished mid-decomposition does not strand the missing children. **A parked unit (0168) holds a non-expiring `parked` state** woken only by an answer or its wake date (0178), never by a lapse.
3. **Status.** The tracker issue of the unit carries state changes and progress as comments (writes follow the project's tracker answer, 0160). A project without a tracker computes status from the claim refs and merged state. Status of a parent is **computed on read** from its children, never stored (0174). Where the sources disagree the order is: the claim ref, then the acceptance record, then the tracker issue, then the plan marker; a marker is set `[x]` only after the unit's `Accept` has passed (or it has none), and `plan status` and `work tree` report any disagreement. This narrows 0117, whose rule that the issue's state decides applies below the claim ref and the acceptance record.
4. **No shared board.** The `Status board` and the in-commit `Progress` lines of the 2026-11-01 roadmap are retired: a step's marker changes in the unit's own PR, and nothing else records live state in git. The product index holds no step state.
5. **Holder identity.** A claim names who holds it; a claim whose holder does not match the author of the commits on the unit's branch is flagged (guardrail `a-claim-names-its-holder`). Signing claims is deferred.
6. **Workers without git push access** claim, release, answer an ask and report a reading through the tracker issue (a comment in a fixed grammar), and a CI job mirrors an accepted comment into the claim ledger and the readings refs. Only commenters listed in the project's worker file (`docs/workers.md`: id, tracker login, kind, capability tags) are accepted; any other comment is ignored with a reply. Git remains the source of truth for exclusion, so a tracker claim is exclusive only once the mirror has created the ref and replied.

## Why

A shared status file is touched by every PR, so at thousands of units it is a permanent merge conflict and a place where stale state hides. One ref updated by compare-and-swap is the one git primitive that gives an atomic check-and-update on every git host with no service to run, which keeps 0015 and `no-runtime-dependencies`. Tracker assignment is not atomic and has no expiry; front-matter claims race at merge time.

## Tradeoffs considered

- **Tracker issue only:** simple and human-friendly, but not atomic, no lease expiry, and makes the tracker mandatory against 0117.
- **Claim in plan front matter:** needs no tracker, but two actors learn of a clash only at merge.
- **Cost accepted:** thousands of refs and heartbeats load the git remote, and tracker comments are rate-limited, so heartbeats stay in the ref and the tracker sees only state changes.
