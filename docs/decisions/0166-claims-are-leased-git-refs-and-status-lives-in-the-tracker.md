## Decision

1. **Claim.** Live claims are entries in a ledger, one ledger per feature: the remote ref `refs/go-getter/claims/<feature-stem>` (one level, so no ledger ref is a prefix of another), a commit whose tree holds one file per entry, `<local-id>.json`, so a new commit shares every unchanged entry with its parent. An entry records the unit, the holder (kind `human|agent|ci`, and an id), the issuer, the scope tokens, the `created` time, the lease expiry, the brief version (0173), the state with its counters (every state of 0173 item 1, failures, claimants), the grant (0171), the parent entry and, for a unit created by delegation that has not merged yet, its brief fields (scope, `Accept`, what to do, `Done-when`, budget), capped in size (a pack answer, default 8 KB; a larger brief spills to the tracker issue). A unit with live children holds no scope tokens (its children do). To claim, a worker fetches the feature's ledger and checks in that version that no live entry holds the same unit or an overlapping scope (0167); a delegated, approved child is claimable by any eligible worker, and its own ancestors' entries do not conflict with it. It adds its entry in a commit it authors and pushes that commit as a fast-forward of the version it read. The host refuses a push that is not a fast-forward, so that refusal is the compare-and-swap; a rejected claimant re-fetches, re-checks and retries with bounded backoff. Force-push is never used (0171 item 4). Exactly one of two overlapping claimants succeeds, ordered by the atomic update and not by a clock. Renewal, parking and release are further commits that change only the lease, state or scope fields. The ledger history is the record of every holder of every unit (0172 item 2).
2. **Lease and renewal.** The lease depends on the holder's kind (pack answers; defaults: agent 60 minutes, ci the job's time limit, human 8 hours). Liveness uses time, so it is judged with a skew margin: an entry is lapsed only after its expiry plus `clock-skew` (a pack answer, default 5 minutes), and a worker compares its clock with the host's `Date` header on every fetch and refuses to claim or take over when they differ by more than the margin. Renewal does not touch the ledger: `heartbeat`, every `go-getter` verb and the generated pre-commit and pre-push git hooks fast-forward the worker's own `refs/go-getter/heartbeat/<worker-id>` with a tiny commit, only when less than half the lease remains and not offline, and an entry's lease runs to the later of its expiry and that worker's last heartbeat plus the lease. Each heartbeat push also pushes the unit's checkpoint ref `refs/go-getter/checkpoints/<unit>`, so a lapse leaves a resumable point (0173 item 2). **A unit with live child units has no lease:** its claim ends when all its children are done, cancelled or superseded, or when its holder releases it; accountability for it is the `Owner-id`, not the holder's heartbeat. If its holder neither acts on the unit nor renews any child for `parent-idle` (a pack answer, default 7 days), the unit is parked with an ask to its `Owner-id`. **A parked unit (0168) holds a non-expiring `parked` state** woken only by an answer or its wake date (0178), never by a lapse. Ledger, heartbeat and checkpoint pushes are made by go-getter itself with a re-entry guard, so the pre-push hook does not fire on them, and they are `work` verbs, not the outward `git-push` of 0161.
3. **Status.** The tracker issue of the unit carries state changes and progress as comments (writes follow the project's tracker answer, 0160). A project without a tracker computes status from the claims ledger and merged state. Status of a parent is **computed on read** from its children, never stored (0174). Where the sources disagree the order is: the claims ledger, then the acceptance record, then the tracker issue, then the plan marker; a marker is set `[x]` only after the unit's `Accept` has passed (or it has none), and `plan status` and `work tree` report any disagreement. This narrows 0117, whose rule that the issue's state decides applies below the claims ledger and the acceptance record.
4. **No shared board.** The `Status board` and the in-commit `Progress` lines of the 2026-11-01 roadmap are retired: a step's marker changes in the unit's own PR, and nothing else records live state in git. The product index holds no step state.
5. **Identity and attribution.** A claim names who holds it, and an entry is valid only if the commit that created it was authored by its holder or issuer; a reader ignores an entry that is not, and an entry's grant, issuer and scope are immutable once written (only lease, state, counters and scope-release change). The claim whose holder does not match the author of the unit's branch commits is flagged (guardrail `a-claim-names-its-holder`). Signing claims (git SSH signing) makes the author check strong and is a later step; until then attribution stops mistakes and casual forgery, not a worker that uses another's credentials, and 0171 item 6 states what that means for grants. Every write path runs the secret and personal-data scan on each field before it pushes and refuses a push that matches, because the pull-request scan (`no-secrets-in-added-lines`) does not see refs.
6. **Workers without git push access** claim, release, answer an ask and report a reading through the tracker issue (a comment in a fixed grammar), and a CI job mirrors an accepted comment into the claims ledger and the readings refs. Any accepted comment by a unit's holder renews its lease (an empty `/renew` is enough), so a field worker on a long lease is not lost. Only commenters listed in the project's worker file (`docs/workers.md`: id, tracker login, kind, capability tags) are accepted; any other comment is ignored with a reply. Git remains the source of truth for exclusion, so a tracker claim is exclusive only once the mirror has created the ref and replied.

## In force

This decision takes effect with K2 (claims and the ledger); until then the status board and `Progress` lines of the existing plans apply and nothing is claimed. Until then the existing practice applies.

## Why

A shared status file is touched by every PR, so at thousands of units it is a permanent merge conflict and a place where stale state hides. One ref updated by compare-and-swap is the one git primitive that gives an atomic check-and-update on every git host with no service to run, which keeps 0015 and `no-runtime-dependencies`. Tracker assignment is not atomic and has no expiry; front-matter claims race at merge time.

## Tradeoffs considered

- **Tracker issue only:** simple and human-friendly, but not atomic, no lease expiry, and makes the tracker mandatory against 0117.
- **Claim in plan front matter:** needs no tracker, but two actors learn of a clash only at merge.
- **Cost accepted:** thousands of ledger commits and heartbeat refs load the git remote, and tracker comments are rate-limited, so heartbeats stay in the ref and the tracker sees only state changes.
